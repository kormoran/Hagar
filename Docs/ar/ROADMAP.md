# 0. الخطة الحالية (بعد 0.6.0)

## 0.1 ترتيب الإصدارات التالية

| الإصدار | الهدف | الحالة |
|---|---|---|
| **0.6.0** | أمان وقت التشغيل + AIsh | مُطلَق |
| **0.7.0** | dev.run + box + Hagar Flow | قيد التطوير |

## 0.1.1 0.7.0 — التنسيق المحلي

- `dev.run` بوصفات موثوقة خارج صندوق الرمل؛
- `box.list` و`box.run` لتحويلات LLM المحدودة (bounded)؛

- أوليات الذاكرة للقراءة فقط: `memory.search` و`memory.context`

- إصلاح صريح بـ `flow.repair`؛
- لا وضع حاويات (container mode) في هذا الإصدار.

## 0.2 0.8.0 — وسيط الـ LLM

- بطاقات تقنية JSON ومعايير قياس النماذج (`/models test`)؛
- اكتشاف العتاد CPU/RAM/GPU (`/models hardware`)؛
- `ModelRegistry` مع context window واستدعاء الأدوات والأسعار وزمن الاستجابة
  والموقع؛
- `TaskProfile` مع الأدوات المطلوبة وحساسية البيانات والميزانية والسياق؛
- توجيه بالقواعد/التنقيط، لا "نموذج LLM يختار النموذج"؛
- اقتراح `AgentSpec` يتحقق منه المضيف؛
- الوسيط لا يمنح أذونات أبدًا: بل يمكنه فقط اقتراح مجموعة جزئية؛
- تجاوز بشري وتدقيق `broker.decision`.

## 0.3 0.8.0 — أداة SQL

- القراءة فقط في الإصدار الأول؛
- SQLite `mode=ro`، و`PRAGMA query_only`، وتعليمة واحدة؛
- لا `ATTACH` ولا `PRAGMA` للكتابة ولا `load_extension`؛
- مهلة، وحد للأسطر/البايتات، وتدقيق للاستعلام؛
- أسماء قواعد بيانات مُعدّة، لا مسارات عشوائية أبدًا؛
- القدرة `DATABASE_READ`؛
- الكتابة وقواعد البيانات الشبكية في مرحلة لاحقة فقط، مع
  `DATABASE_WRITE` و`NETWORK`.

## 0.4 نقاط مفتوحة

- سير عمل الإصدار لا يكون idempotent إذا كان الإصدار موجودًا بالفعل؛
- PyPI: مؤجَّل؛
- MCP OAuth Atlassian: Basic تعمل، ويبقى تدفق OAuth بحاجة إلى

## 0.4.1 نسخة نظام الملفات الكاملة — مجمَّدة

المُنفَّذ الآن:

- `edit_file` بكتابة ذرّية؛
- checkpoint الدور و`/undo`؛
- مهلة لكل أداة وحارس تكرار (repeat guard)؛
- output spill وضغط السياق.

الـ MVP المُنفَّذ يغطي `edit_file`، والكتابة الذرّية،
والقراءة قبل الاستبدال/الحذف/إعادة التسمية، ونسخة `mtime_ns+size`.
والنسخة الكاملة مجمَّدة؛ ولا تدخل الإصدار التالي:

- `edit_file` برقعة متعددة الـ hunk وdiff؛
- بصمة المحتوى (hash) إضافة إلى `mtime_ns`/`size`؛
- كتابة ذرّية بفحص CAS على مستوى نظام الملفات؛
- المراقبة لكل وكيل بمعزل صريح بين الأب و
  الوكلاء الفرعيين؛
- تدقيق `fs.observed` و`fs.guard_denied` و`fs.stale`؛
- تغطية إعادة التسمية/الحذف للمجلدات؛
- تكامل الواجهة الرسومية ورسائل الاستعادة الموجَّهة.

## 0.4.2 AIsh — مُنفَّذة في 0.6.0

`aish.exec` صدفة دلالية فوق أدوات Hagar، بسياسة `DENY`
افتراضية. الأوامر المُنفَّذة: التنقل، والقراءة، والنص الخالص،
والأنابيب، وتعديلات الملفات المفردة. وهي لا تنفّذ برامج مضيف،
ولا إعادة توجيه، ولا متغيّرات، ولا command substitution.
و`text.transform` توفّر العمليات النصية المحدودة (bounded) التي تستخدمها AIsh.

## 0.4.3 dev.run — مُنفَّذ

`dev.list` و`dev.run` ينفّذان وصفات موثوقة للاختبار والتنقيح والبناء.
و`recipes.yaml` خارج صندوق الرمل، ويُقرأ عند الإقلاع ولا يوجد
hot reload. و`DEV_EXEC` هي DENY افتراضيًا؛ والواجهة الخلفية هي المضيف فقط.

وتبقى الحاوية مجمَّدة من أجل وصول مباشر مستقبلي إلى
نظام ملفات/برامج حقيقية، لا داخل صندوق الرمل أبدًا.

## 0.4.4 Boxed transform — مُنفَّذة

`box.list` و`box.run` ينفّذان `summarize` و`translate` و
`extract_json` مع prompt ثابت، وإدخال/إخراج على ملفات، ولا ذاكرة
ولا أدوات. و`BOX_EXEC` هي DENY افتراضيًا.

وهي أوليات الـ DSL المستقبلي.

## 0.4.5 Hagar Flow — MVP

`flow.run` ينفّذ مجموعة فرعية خطية من Python مع مدقّق AST و
مفسّر Hagar، دون `eval`/`exec`. أوليات `fs.*` و`box.*`، وحدود
للخطوات واستدعاءات الأدوات. و`FLOW_EXEC` هي DENY افتراضيًا.

ويبقى HIR والتوازي والوكلاء الفرعيون خارج الـ MVP.

## 0.5 التوثيق

`Docs/it` هو المصدر الوحيد المُصان أثناء التطوير. والمجلدات
`Docs/en` و`Docs/es` و`Docs/zh` و`Docs/ru` و`Docs/pt` و`Docs/ar`
تُعاد توليدها فقط عند إعداد إصدار.

  `candidate` مع `auto_saved: true`؛

  بالرموز) و`memory.project_context` للتفاصيل؛
- `project_max_active` لطلب أرشفة المشروع؛
- استشارة الأرشيف بـ `memory.archive_search` و

ما يبقى: الاحتفاظ بالمحادثات، والبحث الدلالي، والواجهة الرسومية.

## 1.1 القرارات المتخذة

- **الذاكرة العرضية يكتبها الـ harness.** فتُسجَّل أدوار المحادثة
  من الـ harness افتراضيًا: وهو محضر ميكانيكي، لا حكم من
  النموذج. فلا دور مفقود ولا ذكرى مختلقة.
- **الذاكرة الدلالية يكتبها الـ LLM، عند الطلب.** ولا يمكن للنموذج اقتراح
  ذكرى (مهارة) إلا عبر أداة مخصصة. فالاقتراح
  صريح وقابل للنسبة والمراجعة — والقانون الأول يمنع
  التعامل معه كحقيقة.
- **Vault Obsidian فقط.** لا كتابة على نظام الملفات الحقيقي من أجل
  الذاكرة (حاليًا). ويبقى `filesystem.sandbox` صندوق الرمل التشغيلي.
- **الـ Vault لا يُعاد كتابته.** فالأدوات تضيف ملاحظات أو أقسامًا؛ ولا
  تستبدل ملاحظات صانها المستخدم.
- **مشاريع صريحة.** يُختار المشروع عند الإقلاع من قائمة
  المشاريع النشطة، أو بـ `--project`؛ و`--free` و"النشاط
  الحر" بلا ذاكرة مشروع.
- **قرارات المشروع.** منفصلة عن المهارات: فهي تسجّل
  القرارات والبدائل والتبريرات. وتُقترَح كـ `candidate`
  وتُراجَع في نهاية الجلسة؛ وإذا رُفضت المراجعة بقيت
  مرشحة مع `auto_saved: true`، ولا تصبح حقيقة تلقائية.
- **لا حصص رموز.** فالسياق محدود بالبناء:
  فهرس المشروع وعناوين القرارات والملخص و
  `max_context_chars` بالحروف. ولا تُقاس context window الخاصة
  بالنموذج.
- **أرشفة، لا حذف.** فالنصوص والقرارات المؤرشفة
  تبقى في الـ Vault؛ وأرشفة مشروع قابلة للعكس.

## 1.2 الأدوات المتوقعة

أسماء مُنفَّذة في فضاء الأسماء `memory.*`:

| الأداة | من يستدعيها | ما تفعله |
|---|---|---|
| `memory.create_skill` | LLM | ينشئ ذكرى دلالية **مرشحة** |
| `memory.list_skills` | LLM | يسرد الذكريات المتاحة |
| `memory.get_context` | LLM | يسترجع أدوار محادثة سابقة |

التوقيعات المُنفَّذة:

```text
memory.create_skill(title, content, kind="procedure", tags=None)
    -> {id, title, kind, status, tags, created_at, source_*, path, duplicate}

memory.list_skills(kind=None, status=None, limit=20)
    -> [{id, title, kind, status, tags, created_at, source_*}]

memory.get_context(limit=5, query=None, session=None)
    -> [{session, turn, timestamp, question, answer}]
```

السلوكيات:

- `create_skill`: slug من العنوان، وإزالة التكرار بالـ slug، وحد
  للطول (`max_skill_chars`)، وfrontmatter يحتوي `status: candidate`
  و`source_session` و`source_turn` و`model` و`created_at`؛ وإذا وُجد
  slug مطابق يعيد المعرّف الموجود بدلًا من التكرار.
- `list_skills`: يقرأ الـ frontmatter والجسم (لأنه يلزم للاسترجاع)، وقابل للترشيح
  حسب `kind` (`fact` / `procedure`) و`status`.
- `get_context`: بدون `session` يبحث في جميع الجلسات؛ ومع `query`
  يبحث بكلمات مفتاحية في الأدوار السابقة؛ ويُقيَّد `limit` بـ
  1..50 حتى لا يُسكَب الـ Vault كله في السياق.

## 1.5 سلوك الـ harness

- في نهاية الدور: يضيف السؤال والرد إلى ملاحظة الجلسة
  (المحادثة فقط، **لا** مخرجات الأدوات: فتلك تبقى في التدقيق).
- في بداية الدور: يحقن آخر `context_turns` دورًا وحتى
  `context_skills` مهارة **مؤكدة** ذات صلة (بالمطابقة المعجمية)،
  دون انتظار أن يستدعي النموذج `get_context`.
- كل كتابة أو مراجعة للذاكرة تنتج حدث تدقيق
  (`memory.enabled` و`memory.disabled` و`memory.context` و`memory.turn`
  و`memory.review` و`memory.status` و`memory.failed`)؛ وغياب الـ Vault أو
  عدم قابليته للكتابة لا يوقف الـ harness.
- الذاكرة العرضية منفصلة عن التدقيق: فيبقى التدقيق جنائيًا و
  يحتوي أيضًا بيانات الأدوات.

## 1.6 نقاط مفتوحة

- **الاحتفاظ بالمحادثات**: كم جلسة تُحفظ، وهل تُلخَّص
  القديمة؛ و0.2.0 لا تحذف شيئًا.
- **البحث**: فهرس (SQLite FTS) أو embedding عندما تنمو
  الأحجام؛ واليوم هو بالكلمة المفتاحية.
- **الواجهة الرسومية**: تأكيد ASK بحوار نمطي أيضًا لكتابات
  الذاكرة وللمراجعة.
- **اختيار السياق**: اليوم أدوار حديثة عامة، وفهرس
  المشروع، وأعلى 3 مهارات مؤكدة بالمطابقة المعجمية، دون
  صلة دلالية.
- **توطيد القرارات**: يمكن أن يتجاوز المشروع
  `project_max_active`؛ واليوم يقترح Hagar الأرشفة، لا
  دمج القرارات المكررة.

## 1.7 أهداف غير مقصودة (حاليًا)

- كتابة ذكريات على نظام الملفات الحقيقي؛
- تعديل ملاحظات المستخدم الموجودة؛
- embedding / ChromaDB / البحث الدلالي (لاحقًا، إذا برّرت
  الأحجام ذلك)؛
- كتابة ذكريات مستقلة خارج التدفق الصريح.

## 2 الهدف

إزالة هشاشة بروتوكول JSON النصي: لا مزيد من
الإصلاحات، ومعاملات يتحقق منها مخطط المزوّد، ونتائج
مهيكلة.

## 2.1 النهج

- الإبقاء على البروتوكول النصي **كتراجع** للنماذج التي
  لا تدعم الاستدعاء الأصلي أو تفعله بشكل سيئ.
- إضافة قدرة معلنة إلى `LLMClient`
  (`supports_native_tools`) ومسار أصلي.
- يجب أن يتولى الـ `Agent` الاثنين: `ToolCall` نصي أو استدعاء
  أصلي بمعرّف؛ وتعود النتيجة بالصيغة التي يتوقعها المزوّد.
- يقيس المعيار التحسّن (الإصلاحات لكل دور،
  وصحة المعاملات).

## 2.2 النقل لكل مزوّد

| provider | الطلب | نتيجة الأداة |
|---|---|---|
| `ollama` | `tools` في `/api/chat` | رسالة بدور `tool` |
| `deepseek` | `tools` (OpenAI) | دور `tool` + `tool_call_id` |
| `claude` | `tools` + كتل `tool_use` | كتلة `tool_result` |
| `gemini` | `tools.functionDeclarations` | `functionResponse` |

## 2.3 المخاطر

- النماذج المحلية الصغيرة غالبًا لا تستخدم الاستدعاء الأصلي جيدًا: فيلزم
  التراجع التلقائي.
- تتغير بنية تمرير الرسائل: فاختبارات كل مزوّد ومسار
  التراجع إلزامية.
- بعض النماذج تعيد استدعاءات متعددة في الدور نفسه: وينفّذها الوكيل
  جميعًا، في حدود الدور.

- **MCP**: ردود `text/event-stream`، وإشعار
  `notifications/initialized`، وتطبيع النتائج إلى نص
  (كتل `text` و`structuredContent` وأخطاء `isError`).
- **MCP auth**: bearer أو ترويسة مخصصة، والرمز من البيئة فقط،
  ويتخطى الخادم بـ `mcp.failed` إذا غاب الرمز.
- **MCP OAuth**: تدفق authorization code + PKCE مع المتصفح، واكتشاف
  RFC 9728/8414، والتسجيل الديناميكي، وذاكرة الرموز، والتجديد وإعادة المحاولة عند 401.
- **التدقيق**: تدوير عند `max_bytes`، وسلسلة بصمات قابلة للتحقق بـ
  `verify_chain`، وحجب مخرجات الأدوات بـ
  `include_outputs: false`.
- **الاحتفاظ بالتدقيق**: نسخ احتياطية بطوابع زمنية و`audit.max_files` (الافتراضي
  100، ويشمل الملف النشط) مع تقليم الأقدم.
- **عنوان URL الأساسي**: `model.host` يسري لجميع المزوّدين.

ما يبقى:

- device flow / DPoP لـ MCP OAuth؛
- ضغط جلسات التدقيق؛
- المواءمة المستمرة للتوثيق.

# 9. الأدوات المحلية

الحالة في 2026-11-05:

- نظام الملفات v2: `list_dir` و`read_chunk` و`rename` و`copy_file`
  و`search`، إضافة إلى الأدوات الموجودة؛
- `local_tools/`: `calculator.evaluate` و`statistics.compute`
  و`units.convert` و`feed.read` (مزوّدون محليون، لا خوادم MCP)؛
- القدرة `COMPUTE` في السقف دائمًا، و`NETWORK` يتحكم بها
  `permissions.network` والسياسة (وfeed في `ask`)؛
- حدود الكتابة: `max_write_bytes` و`min_free_bytes`
  و`session_write_bytes` و`ask_over_bytes` مع فحص مسبق واحد؛
- `feed.read` بسياسة SSRF: عناوين عامة فقط، وإعادة توجيه
  يُعاد التحقق منها، ولا بيانات اعتماد في عنوان URL؛
- نظام ملفات بجذر افتراضي `/home/ai`، وأسماء مستعارة إلزامية و
  أذونات لكل mount (`R`/`W`/`X`)؛
- مشغّل POSIX `tools/run_tests.sh` إلى جانب مشغّل Windows.

نقاط مفتوحة:

- DNS rebinding: يُتحقق من التحليل، لكن `requests` يحل
  الاسم مرة أخرى عند الاتصال؛ ويلزم resolver مثبَّت
  أو محوّل مخصص لإغلاق الحالة؛
- الآلة الحاسبة محدودة عن قصد (لا جبر رمزي)؛
- تقييم حد للحجم أيضًا لمخرجات الأدوات الأخرى.

مغلق كمسؤولية المستخدم:

- الروابط الصلبة وmount وjunction داخل المجلدات المسموح بها لا
  يتحقق منها Hagar. ولعزل تام يجب على المستخدم ضمان
  عدم وجودها؛ وHagar لا ينشئها ولا يكتشفها؛
- سباق TOCTOU: لا يستخدم Hagar `openat2` ولا `O_NOFOLLOW` على كل مكوّن ولا
  مقابض Windows ولا يضمن الذرّية بين الفحص والعملية. فالسباق
  يتطلب عملية محلية متزامنة بوصول للكتابة؛
  وهو سيناريو خبيث أو بيئة مخترقة، لا استخدام عادي.
  ولعزل تام يلزم مجلد تخزين مخصص، أو مستخدم منفصل، أو mount
  namespace، أو حاوية.
