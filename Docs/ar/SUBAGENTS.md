# الوكلاء الفرعيون — المرحلة غير المتزامنة

**الحالة:** منفَّذ
**التاريخ:** 2026-11-07
**الأدوات:** `agent.spawn`، `agent.status`، `agent.wait`، `agent.result`،
`agent.cancel`، `agent.run` (توافق متزامن)، `artifact.*`،
`mailbox.*`

## 1. ما الذي تفعله

يمكن للنموذج تشغيل حتى وكيلين فرعيين متزامنين:

```text
agent.spawn(task, reason, context?, inputs?) -> agent_id
agent.status(agent_id) -> الحالة
agent.wait(agent_id, timeout?) -> النتيجة
agent.result(agent_id) -> النتيجة
agent.cancel(agent_id) -> ok
```

يعود `spawn` فورًا. ويمكن للأب مواصلة العمل وجمع النتائج عند الحاجة.
ويبقى `agent.run` اختصارًا لـ `spawn + wait` من أجل التوافق.

`reason` إلزامي: يُسجَّل في التدقيق وهو التبرير الذي من أجله يفوّض الأب
العمل. وتتطلب الأداة القدرة `AGENT_SPAWN`؛ ولا يتلقاها الابن، ولذلك لا
يستطيع إنشاء وكلاء آخرين. و`permissions.agents: true` هو سقف النظام
اللازم.

يجب أن تكون سياسة الابن **أكثر تقييدًا بصرامة** من سياسة الأب. ويحسب
المدير:

```text
child_ceiling = parent_ceiling
              & (FILESYSTEM_READ | MEMORY_READ | COMPUTE | AGENT_DATA)
```

وإذا كانت النتيجة مساوية لسقف الأب، يفشل `agent.spawn` بـ
`SubagentPolicyError`. وبالتالي تُرفض حتى السياسات المتطابقة. وإذا لم
يكن للأب evaluator، يُرفض الـ spawn.

لكل وكيل مهلة زمنية فعلية مدتها **5 دقائق** (`300` ثانية). والحد
تعاوني: يُفحص عند نقاط التحقق في دورة الوكيل؛ ولا يقاطع طلب HTTP جاريًا.
وعند انتهائها تكون حالة الابن `timed_out` ويسجّل التدقيق
`agent.timed_out`.

كل ابن:

- يستخدم النموذج المحلي نفسه الخاص بالأب، لكن عميل LLM منفصل؛
- له سجل منفصل؛
- يرى فقط الأدوات ذات القدرات `FILESYSTEM_READ` و`MEMORY_READ`
  و`COMPUTE`، إضافة إلى `AGENT_DATA`؛
- يمكنه استخدام `vision.open` على مساحة عمله، لكن لا يستطيع استخدام
  `agent.*` ولا `filesystem.chdir`؛
- يقرأ مساحة عمله فقط؛
- لا يكتب في الذاكرة؛
- يمرّر طلبات ASK إلى المستخدم عبر bridge، بمهلة 180 ثانية وDENY عند
  انتهائها.

لا يستطيع الـ LLM الأب الموافقة على ASK: فالطلب يذهب دائمًا إلى القناة
البشرية (الواجهة الرسومية أو الطرفية). ويضيف الـ bridge `agent_id`
و`parent_id` إلى الطلب.

## 2. مساحة عمل خاصة

لكل ابن تُنشأ مساحة عمل مؤقتة:

```text
<hagar-temp>/hagar-subagent-<id>/
```

ويراها الابن على النحو التالي:

```text
/home/ai/workspace
```

مساحة العمل للقراءة فقط. وقبل الإقلاع، ينسخ المدير المدخلات التي
يشير إليها الأب:

```text
agent.spawn(
    task="حلّل ملف CSV",
    reason="الملفات مستقلة ويجب تحليلها بالتوازي",
    inputs=["/home/ai/workspace/report.csv"]
)
```

القواعد:

- يجب أن تكون المدخلات ملفات داخل صندوق الرمل الخاص بالأب؛
- يجب أن يملك الأب إذن القراءة؛
- يُحفظ اسم الملف؛
- وجود مدخلين بالاسم نفسه خطأ؛
- لا يرى الابن مسار المضيف؛
- تُحذف مساحة العمل في نهاية الدور.

يكتب الأب في مساحة عمله فقط. ومساحة عمل الابن خارج جذور الأب، ولذلك لا
تصل إليها أدواته.

## 2.1 صندوق الصادر وartifact وmailbox

لا يكتب الابن في مساحة العمل. ولإنتاج بيانات يستخدم صندوق الصادر:

```text
artifact.put(text, kind?, mime_type?)       -> artifact_id
artifact.put_file(path, mime_type?)          -> artifact_id
mailbox.send(text, artifacts?)               -> message
```

يقرأ `artifact.put_file` ملفًا من مساحة عمل الابن ذات القراءة فقط
وينسخه إلى المخزن الذي يديره Hagar.

ويقرأ الأب بـ:

```text
artifact.list()
artifact.read(artifact_id, offset?, length?)
artifact.save_to(artifact_id, path, overwrite?)
mailbox.inbox(cursor?, limit?)
mailbox.read(message_id)
mailbox.ack(message_id)
```

ينسخ `artifact.save_to` الـ artifact بأكمله إلى مسار قابل للكتابة في
صندوق رمل الأب دون تمرير المحتوى عبر السياق. وهي العملية التي تُستخدم
من أجل artifacts أكبر من نافذة النموذج: فيقرأ النموذج فقط المقاطع التي
يحتاجها ويحفظ الملف كاملًا بـ `save_to`.

يتطلب `save_to` القدرات `AGENT_DATA` و`FILESYSTEM_WRITE`
و`FILESYSTEM_CREATE`؛ وتتعامل معه السياسة كعملية كتابة وقد تطلب تأكيدًا.
ولا يقبل مسارات مضيف عشوائية.

الحدود الأولية:

| العنصر | الحد |
|---|---|
| artifact واحد | 50 MB |
| إجمالي الـ artifacts لكل دور | 256 MB |
| الـ artifacts لكل دور | 200 |
| القراءة لكل استدعاء | 256 KB |
| نص الرسالة الواحدة | 64 KB |
| الرسائل لكل mailbox | 100 |

الـ artifacts ملفات مؤقتة خارج الـ Vault، ببصمة SHA-256 وبيانات وصفية.
ولا يحتوي الـ mailbox إلا على نص ومراجع `artifact_id`. وفي نهاية الدور
يُفرَّغ المخزن والـ mailbox.

## 3. حدود التنفيذ

- بحد أقصى **2** وكيلين فرعيين نشطين (قابل للإعداد في المدير كـ
  `max_concurrent`)؛
- النماذج المحلية فقط؛
- لا تداخل: فسجل الابن يستبعد `agent.*`؛
- مهلة زمنية فعلية مدتها 5 دقائق، تعاونية؛
- لا ميزانية رموز إضافة إلى `max_tool_calls`؛
- لا واجهة رسومية مخصصة؛
- لا كتابة في الذاكرة؛
- تأكيدات ASK الخاصة بالابن تُمرَّر إلى المستخدم بمهلة 180 ثانية؛ وعند
  انتهائها DENY؛
- الـ artifacts والـ mailbox مؤقتة: تختفي في نهاية الدور؛
- الأحداث الداخلية للابن (`turn.*` و`tool.*`) تحمل `agent_id` في
  التدقيق.

في نهاية دور الأب:

1. ينتظر `finish_turn()` الأبناء لمهلة محددة؛
2. يلغي من لا يزال نشطًا منهم؛
3. يحذف مساحات العمل؛
4. ينسى المهام.

## 4. المكوّنات المعزولة

| المكوّن | الأب | الابن |
|---|---|---|
| LLM client | `harness.llm` | نسخة جديدة، النموذج نفسه |
| Tool registry | كامل | مرشَّح للقراءة فقط |
| نظام الملفات | مساحة عمل الأب | مساحة عمل خاصة للقراءة فقط |
| الذاكرة | `MemoryStore` | `memory=None`، بلا كتابة |
| Artifact/mailbox | قراءة | صندوق صادر الابن |
| التأكيدات | المستخدم | bridge نحو المستخدم، بمهلة 180 |
| Usage | ledger الأب | ledger منفصل |
| التدقيق | مشترك، بقفل | أحداث `agent.*` |

لا يملك الابن سياق الأب التلقائي: فيجب على الأب تمرير `context`.

## 5. الأدوات المسموح بها

يجب أن يملك الأب القدرتين `AGENT_SPAWN` و`COMPUTE`؛ ولا يتلقى الابن
`AGENT_SPAWN` وبالتالي لا يستطيع إنشاء وكلاء آخرين.

يشمل سجل الابن الأدوات التي تكون قدراتها مجموعة جزئية من:

```text
FILESYSTEM_READ
MEMORY_READ
COMPUTE
AGENT_DATA
```

ويتلقى الابن `artifact.put` و`artifact.put_file` و`mailbox.send`. ولا
يتلقى `artifact.read` ولا `artifact.list` ولا `mailbox.inbox` ولا
`mailbox.read` ولا `mailbox.ack`: فتلك خاصة بالأب.

ويُستبعد صراحةً:

```text
filesystem.chdir
agent.*
```

ويُستبعد حسب القدرة:

- الكتابة في نظام الملفات؛
- الإنشاء وإعادة التسمية والنسخ والحذف؛
- الكتابة في الذاكرة؛
- الشبكة؛
- MCP؛
- shell.

## 6. التدقيق

الأحداث التي يسجّلها المدير:

```text
agent.spawned
agent.policy_rejected
agent.started
agent.finished
agent.timed_out
agent.cancelled
agent.failed
confirmation.timeout
artifact.discarded
```

الحقول الرئيسية:

```text
agent_id
agent
parent
task
inputs
max_tool_calls
max_seconds
status
usage
duration_ms
error
artifact
owner
kind
size
sha256
read_count
reason
```

جميع أحداث الأب والأبناء تحمل `agent_id`. وأحداث السجل والوكيل تستخدم
معرّف الوكيل الذي نفّذ الفعل؛ وأحداث المدير تضيف `agent_id` و`parent`.
ويُصدر `agent.policy_rejected` إذا لم يكن للـ spawn سياسة أكثر تقييدًا
بصرامة.

ويُصدر `artifact.discarded` في نهاية الدور لكل artifact لم يُحفظ بـ
`artifact.save_to`:

```text
reason=unread                → لم يُقرأ قط
reason=read_but_not_saved    → قُرئ لكن لم يُصدَّر
```

ويُصدر `confirmation.timeout` إذا بقي ASK الخاص بالابن دون رد لمدة 180
ثانية؛ والنتيجة DENY. وتعرض الواجهة الرسومية الطلب مع
`agent_id`/`parent_id` ولا يستطيع الأب حلّه.

والـ artifacts المُصدَّرة لا تنتج الحدث: فالملف موجود بالفعل في مساحة عمل
الأب. ولا يُكتب المحتوى أبدًا في التدقيق.

`AuditLog.record` محمي بقفل، وبذلك لا تتداخل الكتابات المتزامنة في سلسلة
البصمات.

## 7. التزامن

- خيوط منفصلة للأبناء؛
- الحد `max_concurrent = 2`؛
- قفل على قاموس المهام؛
- لا حالة سباق على نظام الملفات: فمساحات العمل منفصلة؛
- لا مشاركة لـ `MemoryStore` أو صندوق الرمل أو عميل LLM؛
- مزوّد محلي بطلبات متزامنة؛
- `agent.wait` يحجب المستدعي فقط، لا الأبناء الآخرين.

## 9. الخطوات التالية

- تصدير صريح للـ artifacts من مساحة عمل الابن؛
- ميزانية رموز/وقت ومهلة زمنية فعلية؛
- تداخل مُتحكَّم فيه، إذا لزم؛

- نموذج يختاره الوسيط، لا المدير.
