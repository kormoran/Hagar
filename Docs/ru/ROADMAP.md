# HAGAR — Roadmap

Текущая версия: 0.2.0 (в разработке)
Последнее обновление: 2026-11-03

Принятые решения помечены как таковые; всё ещё открытые вопросы
перечислены в конце каждой области.

---

# 1. Направление

Hagar прошёл путь от «идеи» до «работающей системы» (v0.1), а затем до
harness с аудитом, несколькими backend и набором тестов (v0.2 в работе). Следующий
шаг — не добавление инструментов: это дать системе **память** и
способ вызова инструментов, менее хрупкий, чем текстовый JSON.

Принятый порядок:

1. память на Vault;
2. нативный вызов для провайдеров, которые его поддерживают;
3. PermissionEvaluator — **v1 сделана** (policy.yaml, ASK, аудит);
4. гигиена (аудит, MCP, упаковка, live-тесты).

# 2. Приоритет 1 — Память на Vault

## 2.0 Статус: v2 реализована (2026-11-04)

Реализовано:

- эпизодическая память, записываемая harness, одна заметка на сессию;
- автоматическое внедрение последних `context_turns` ходов;
- инструменты `memory.create_skill`, `memory.list_skills`, `memory.get_context`;
- происхождение (`source_session`, `source_turn`, `model`), состояние
  `candidate`, дедупликация по slug;
- политика `MEMORY_READ`/`MEMORY_WRITE` и пространства имён `chat` / `skills`;
- отсутствие vault → память отключается с предупреждением, harness активен;
- жизненный цикл `candidate` → `confirmed` → `archived` с человеческой проверкой
  из CLI (`/memory review`, `confirm`, `archive`);
- автоматическое внедрение только подтверждённых навыков, топ-3 по лексическому
  совпадению;
- retention вариант A: никакого автоматического удаления, только архив;
- память проекта, отдельная от навыков: решения, альтернативы,
  обоснования, состояние и происхождение;
- выбор проекта при запуске, `--project`/`--free`, команды
  `/project`;
- сводка в конце сессии с fallback, транскрипт в `archive/chat/`
  и ссылка/хеш в сводке;
- проверка решений в конце сессии; при отказе они остаются
  `candidate` с `auto_saved: true`;
- контекст в виде индекса с бюджетом `max_context_chars` (символы, а не
  токены) и `memory.project_context` для деталей;
- `project_max_active` для запроса архивирования проекта;
- обращение к архиву с помощью `memory.archive_search`,
  `memory.archive_read`, `/memory archive search|read`, фильтр по
  проекту и транскрипт с `project` в frontmatter.

Остаётся: retention чатов, семантический поиск, GUI.

## 2.1 Принятые решения

- **Эпизодическая память пишется harness.** Ходы чата регистрируются
  harness по умолчанию: это механический протокол, а не суждение
  модели. Ни один ход не теряется, ни одна память не выдумывается.
- **Семантическая память пишется LLM, по запросу.** Модель может предложить
  воспоминание (навык) только через специальный инструмент. Предложение
  явное, атрибутируемое и проверяемое — Первый закон запрещает
  трактовать его как истину.
- **Только Vault Obsidian.** Никакой записи в реальную файловую систему для
  памяти (пока). `filesystem.sandbox` остаётся операционной sandbox.
- **Vault не перезаписывается.** Инструменты добавляют заметки или разделы; они не
  перезаписывают заметки, выверенные пользователем.
- **Проекты задаются явно.** Проект выбирается при запуске из списка
  активных проектов либо с помощью `--project`; `--free` и «свободная
  работа» не имеют памяти проекта.
- **Решения проекта.** Они отделены от навыков: фиксируют
  решения, альтернативы и обоснования. Предлагаются как `candidate`
  и проверяются в конце сессии; если проверка отклонена, они остаются
  кандидатами с `auto_saved: true` и не становятся автоматической истиной.
- **Без токеновых квот.** Контекст ограничен по построению:
  индекс проекта, заголовки решений, сводка и
  `max_context_chars` в символах. Context window модели не
  измеряется.
- **Архив, а не удаление.** Транскрипты и архивные решения
  остаются в Vault; архивирование проекта обратимо.

## 2.2 Запланированные инструменты

Имена, реализованные в пространстве имён `memory.*`:

| инструмент | кто вызывает | что делает |
|---|---|---|
| `memory.create_skill` | LLM | создаёт **кандидата** в семантической памяти |
| `memory.list_skills` | LLM | перечисляет доступные воспоминания |
| `memory.get_context` | LLM | извлекает прошлые ходы чата |

Реализованные сигнатуры:

```text
memory.create_skill(title, content, kind="procedure", tags=None)
    -> {id, title, kind, status, tags, created_at, source_*, path, duplicate}

memory.list_skills(kind=None, status=None, limit=20)
    -> [{id, title, kind, status, tags, created_at, source_*}]

memory.get_context(limit=5, query=None, session=None)
    -> [{session, turn, timestamp, question, answer}]
```

Поведение:

- `create_skill`: slug из заголовка, дедупликация по slug, ограничение
  длины (`max_skill_chars`), frontmatter с `status: candidate`,
  `source_session`, `source_turn`, `model`, `created_at`; если уже существует
  такой же slug, возвращается существующий id вместо создания дубликата.
- `list_skills`: читает frontmatter и тело (нужно для recall), фильтруется
  по `kind` (`fact` / `procedure`) и `status`.
- `get_context`: без `session` ищет во всех сессиях; с `query`
  ищет по ключевым словам в прошлых ходах; `limit` ограничивается
  значениями 1..50, чтобы не выливать весь Vault в контекст.

## 2.3 Структура в Vault

```text
<Vault>/Hagar/
  chat/2026-11-03-<session>.md      # одна заметка на сессию, ходы добавляются в конец
  skills/<slug>.md                  # одна заметка на воспоминание
```

Эпизодическая память (одна заметка на сессию, ходы добавляются в конец):

```markdown
---
session: a1b2c3d4
type: chat
created: 2026-11-03T00:12:44+01:00
---

# Чат 2026-11-03

## 2026-11-03T00:12:44+01:00 · 7f3a

**Пользователь:** ...
**Hagar:** ...
```

Семантическая память (одна заметка на навык):

```markdown
---
id: usa-uv-per-python
title: Использовать uv для проектов на Python
kind: procedure
status: candidate
tags: [python, tooling]
source_session: a1b2c3d4
source_turn: 7f3a
model: llama3.1:latest
created_at: 2026-11-03T00:15:02+01:00
---

Шаги / содержимое, предложенное моделью.
```

## 2.4 Конфигурация

```yaml
vault:
  path: <реальный путь>

memory:
  enabled: true
  vault_subdir: Hagar
  context_turns: 10
  context_skills: 3
  max_skill_chars: 4000
```

## 2.5 Поведение harness

- В конце хода: добавляет вопрос и ответ в заметку сессии (только
  беседа, **не** вывод инструментов: он остаётся в аудите).
- В начале хода: внедряет последние `context_turns` ходов и до
  `context_skills` **подтверждённых** релевантных навыков (лексическое совпадение),
  не дожидаясь, пока модель вызовет `get_context`.
- Каждая запись или проверка памяти порождает событие аудита
  (`memory.enabled`, `memory.disabled`, `memory.context`, `memory.turn`,
  `memory.review`, `memory.status`, `memory.failed`); отсутствующий или
  недоступный для записи Vault не останавливает harness.
- Эпизодическая память отделена от аудита: аудит остаётся криминалистическим и
  содержит также данные инструментов.

## 2.6 Открытые вопросы

- **Retention чатов**: сколько сессий хранить, следует ли резюмировать
  старые; версия 0.2.0 ничего не удаляет.
- **Поиск**: индекс (SQLite FTS) или embedding, когда объёмы
  вырастут; сегодня поиск по ключевым словам.
- **GUI**: подтверждение ASK с модальным диалогом также для записей в
  память и для проверки.
- **Выбор контекста**: сегодня последние глобальные ходы, индекс
  проекта и топ-3 подтверждённых навыков по лексическому совпадению, без
  семантической релевантности.
- **Консолидация решений**: проект может превысить
  `project_max_active`; сегодня Hagar предлагает архивирование, а не
  объединение дублирующихся решений.

## 2.7 Не-цели (пока)

- запись воспоминаний в реальную файловую систему;
- изменение существующих заметок пользователя;
- embedding / ChromaDB / семантический поиск (позже, если объёмы это
  оправдают);
- автономная запись воспоминаний вне явного потока.

# 3. Приоритет 2 — Нативный вызов (v1, сделано)

**Статус:** реализовано 2026-11-03. `native_step()` для четырёх
провайдеров, схема параметров из `ToolDefinition`, канонические сообщения
`tool`, несколько вызовов за ход, автоматический fallback на HTTP 400/404/422
и `--no-native-tools`. Проверено вживую на Ollama и DeepSeek; Claude и
Gemini ещё предстоит проверить. Измерено с помощью `tools/bench_native.py`: ни один
протокол не выигрывает у всех моделей (нативный быстрее, текст иногда точнее).
Остаётся доработать для локальных моделей, которые игнорируют инструменты.

## 3.1 Цель

Устранить хрупкость текстового JSON-протокола: больше никаких
исправлений, аргументы валидируются схемой провайдера, результаты
структурированы.

## 3.2 Подход

- Сохранить текстовый протокол как **fallback** для моделей, которые
  не поддерживают нативный вызов или делают это плохо.
- Добавить в `LLMClient` объявленную возможность
  (`supports_native_tools`) и нативный путь.
- `Agent` должен обрабатывать оба: текстовый `ToolCall` или нативный
  вызов с id; результат возвращается в формате, ожидаемом провайдером.
- Бенчмарк измеряет улучшение (исправления за ход,
  корректность аргументов).

## 3.3 Транспорт для каждого провайдера

| провайдер | запрос | результат инструмента |
|---|---|---|
| `ollama` | `tools` в `/api/chat` | сообщение с ролью `tool` |
| `deepseek` | `tools` (OpenAI) | роль `tool` + `tool_call_id` |
| `claude` | `tools` + блоки `tool_use` | блок `tool_result` |
| `gemini` | `tools.functionDeclarations` | `functionResponse` |

## 3.4 Риски

- Небольшие локальные модели часто плохо используют нативный вызов: нужен
  автоматический fallback.
- Меняется plumbing сообщений: тесты для провайдера и для пути
  fallback обязательны.
- Некоторые модели возвращают несколько вызовов за один ход: Agent
  выполняет их все, в пределах хода.

# 4. Приоритет 3 — PermissionEvaluator

## 4.1 Статус: v1 реализована

Реализовано:

- `Capability`, `Effect`, `Rule`, `Subject`, `Resource`, `Decision` и
  `PermissionEvaluator` в `core/permissions.py`;
- `policy.yaml` читается **до** LLM, с fallback на полный `DENY` и
  предупреждением в аудите и чате;
- системный предел, производный от `permissions.read/write/shell`;
- область действия для `tools` (glob), `paths` и `namespaces` (префиксы);
- `ASK` с `ConsoleConfirmation` (`lo faccio? (y/N)`, по умолчанию N);
- применение в `ToolRegistry.execute` и аудит
  `permission.decision` / `permission.confirmation`;
- `ToolDefinition.capabilities` для всех инструментов (filesystem и MCP);
- `requires_confirmation` применяется как нижняя граница ASK;
- собрано 347 тестов, 1 пропуск.

## 4.2 Что осталось сделать

- `ConfirmationProvider` для GUI (модальный диалог) и для неинтерактивного
  выполнения (deny по умолчанию);
- динамические политики для задачи/роли, только с сужением во время выполнения (агент
  может сузить свои права, но никогда не расширить их самостоятельно);
- capability инструментов MCP, назначаемые конфигурацией, а не
  объявляемые сервером;
- несколько субъектов, выполняющихся одновременно (несколько агентов с разными
  политиками);
- объекты-ресурсы для памяти и путей, а не только для инструментов.

# 5. Приоритет 4 — AIsh

Shell, предназначенный для LLM, концептуально похожий на Bash, но без какого-либо
доступа к настоящему shell:

- никакого выполнения команд хоста;
- исключительное использование зарегистрированных инструментов;
- смоделированная файловая система и виртуальные пути (`workspace://`);
- интеграция с инструментами MCP;
- конвейеры и виртуальные команды.

```text
ls workspace://
cat workspace://project/readme.md
find *.py
```

Виртуальные пути решили бы также проблему раскрытия абсолютных путей
sandbox.

# 6. Гигиена и устойчивость

Сделано (2026-11-03):

- **MCP**: ответы `text/event-stream`, уведомление
  `notifications/initialized`, нормализация результатов в текст
  (блоки `text`, `structuredContent`, ошибки `isError`).
- **MCP auth**: bearer или пользовательский header, токен только из окружения,
  сервер пропускается с `mcp.failed`, если токен отсутствует.
- **MCP OAuth**: поток authorization code + PKCE с браузером, discovery
  RFC 9728/8414, динамическая регистрация, кеш токенов, refresh и повтор при 401.
- **Аудит**: ротация при `max_bytes`, проверяемая цепочка хешей с
  `verify_chain`, редактирование вывода инструментов при
  `include_outputs: false`.
- **Audit retention**: резервные копии с метками времени и `audit.max_files` (по умолчанию
  100, включая активный файл) с удалением самых старых.
- **Live-тесты**: маркер `live`, исключены по умолчанию, `--live` для Ollama
  и удалённых провайдеров (последние пропускаются без ключа).
- **Упаковка**: полные метаданные, entry point `hagar`, `--config`,
  `--model`, `--no-memory`, `--version`, единая версия.
- **Базовый URL**: `model.host` действует для всех провайдеров.
- **Legacy**: удалены `tools/filesystem.py` и `llm/tool_result.py`.

Остаётся:

- device flow / DPoP для MCP OAuth;
- компактизация сессий аудита;
- GUI-подтверждения для `ASK`;
- постоянная синхронизация документации.

# 9. Локальные инструменты

Состояние на 2026-11-05:

- filesystem v2: `list_dir`, `read_chunk`, `rename`, `copy_file`,
  `search`, помимо существующих инструментов;
- `local_tools/`: `calculator.evaluate`, `statistics.compute`,
  `units.convert`, `feed.read` (локальные провайдеры, не серверы MCP);
- capability `COMPUTE` всегда в пределе, `NETWORK` контролируется
  `permissions.network` и политикой (feed в `ask`);
- ограничения записи: `max_write_bytes`, `min_free_bytes`,
  `session_write_bytes` и `ask_over_bytes` с единым preflight;
- `feed.read` с политикой SSRF: только глобальные адреса, redirect
  перепроверяются, никаких учётных данных в URL;
- filesystem с виртуальным корнем `/home/ai`, обязательными alias и
  разрешениями для каждого mount (`R`/`W`/`X`);
- POSIX-runner `tools/run_tests.sh` наряду с Windows-версией.

Открытые вопросы:

- DNS rebinding: разрешение адреса валидируется, но `requests` разрешает
  имя заново в момент соединения; нужен закреплённый resolver или
  специальный адаптер, чтобы закрыть этот случай;
- калькулятор намеренно ограничен (никакой символьной алгебры);
- оценить ограничение размера также для остальных выводов инструментов.

Закрыто как ответственность пользователя:

- hard link, mount и junction внутри разрешённых каталогов не
  контролируются Hagar. Для полной изоляции пользователь должен гарантировать,
  что их нет; Hagar их не создаёт и не обнаруживает;
- гонка TOCTOU: Hagar не использует `openat2`, `O_NOFOLLOW` для каждого компонента или
  дескрипторы Windows и не гарантирует атомарность между проверкой и операцией. Гонка
  требует локального параллельного процесса с доступом на запись;
  это злонамеренный сценарий или сценарий скомпрометированной среды, а не обычное
  использование. Для полной изоляции нужны выделенный том, отдельный пользователь, mount
  namespace или контейнер.
