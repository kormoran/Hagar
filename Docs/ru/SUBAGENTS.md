# Субагенты — асинхронная фаза

**Статус:** реализовано
**Дата:** 2026-11-07  
**Инструменты:** `agent.spawn`, `agent.status`, `agent.wait`, `agent.result`,
`agent.cancel`, `agent.run` (синхронная совместимость), `artifact.*`,
`mailbox.*`

## 1. Что они делают

Модель может запускать до двух параллельных субагентов:

```text
agent.spawn(task, reason, context?, inputs?) -> agent_id
agent.status(agent_id) -> состояние
agent.wait(agent_id, timeout?) -> результат
agent.result(agent_id) -> результат
agent.cancel(agent_id) -> ok
```

`spawn` возвращает управление немедленно. Родитель может продолжать работу
и забирать результаты, когда они понадобятся. `agent.run` остаётся
сокращением `spawn + wait` ради совместимости.

`reason` обязателен: он записывается в аудит и служит обоснованием того,
почему родитель делегирует работу. Инструменту требуется возможность
`AGENT_SPAWN`; ребёнок её не получает, поэтому не может создавать других.
`permissions.agents: true` — это необходимый системный потолок.

Политика ребёнка должна быть **строго более ограничительной**, чем политика
родителя. Менеджер вычисляет:

```text
child_ceiling = parent_ceiling
              & (FILESYSTEM_READ | MEMORY_READ | COMPUTE | AGENT_DATA)
```

Если результат совпадает с потолком родителя, `agent.spawn` завершается
ошибкой `SubagentPolicyError`. Поэтому отклоняются даже идентичные политики.
Если у родителя нет evaluator, spawn отклоняется.

У каждого агента есть абсолютный тайм-аут в **5 минут** (`300` секунд).
Ограничение кооперативное: оно проверяется на контрольных точках цикла
агента и не прерывает уже выполняющийся HTTP-вызов. По истечении срока
состояние ребёнка — `timed_out`, а аудит регистрирует `agent.timed_out`.

Каждый ребёнок:

- использует ту же локальную модель, что и родитель, но отдельный клиент LLM;
- имеет отдельный реестр;
- видит только инструменты с возможностями `FILESYSTEM_READ`,
  `MEMORY_READ` и `COMPUTE`, плюс `AGENT_DATA`;
- может использовать `vision.open` в своём рабочем пространстве, но не
  `agent.*` и не `filesystem.chdir`;
- читает только своё рабочее пространство;
- не пишет в память;
- передаёт запросы ASK пользователю через мост с тайм-аутом
  180 секунд и DENY по истечении срока.

Родительская LLM не может одобрить ASK: запрос всегда уходит в человеческий
канал (GUI или консоль). Мост добавляет `agent_id` и `parent_id` к запросу.

## 2. Приватное рабочее пространство

Для каждого ребёнка создаётся временное рабочее пространство:

```text
<hagar-temp>/hagar-subagent-<id>/
```

Ребёнок видит его как:

```text
/home/ai/workspace
```

Рабочее пространство доступно только для чтения. Перед запуском менеджер
копирует входные данные, указанные родителем:

```text
agent.spawn(
    task="проанализируй CSV",
    reason="файлы независимы и должны анализироваться параллельно",
    inputs=["/home/ai/workspace/report.csv"]
)
```

Правила:

- входные данные должны быть файлами в песочнице родителя;
- у родителя должно быть разрешение на чтение;
- имя файла сохраняется;
- два входных файла с одинаковым именем — ошибка;
- ребёнок не видит путь на хосте;
- рабочее пространство удаляется в конце хода.

Родитель пишет только в своё рабочее пространство. Рабочее пространство
ребёнка находится вне корней родителя, поэтому недоступно его инструментам.

## 2.1 Outbox, артефакты и mailbox

Ребёнок не пишет в рабочее пространство. Для получения данных он
использует outbox:

```text
artifact.put(text, kind?, mime_type?)       -> artifact_id
artifact.put_file(path, mime_type?)          -> artifact_id
mailbox.send(text, artifacts?)               -> message
```

`artifact.put_file` читает файл из рабочего пространства ребёнка,
доступного только для чтения, и копирует его в хранилище, управляемое
Hagar.

Родитель читает с помощью:

```text
artifact.list()
artifact.read(artifact_id, offset?, length?)
artifact.save_to(artifact_id, path, overwrite?)
mailbox.inbox(cursor?, limit?)
mailbox.read(message_id)
mailbox.ack(message_id)
```

`artifact.save_to` копирует артефакт целиком в доступный для записи путь
песочницы родителя, не пропуская содержимое через контекст. Это операция
для артефактов, размер которых превышает окно модели: модель читает только
нужные ей фрагменты и сохраняет полный файл с помощью `save_to`.

`save_to` требует `AGENT_DATA`, `FILESYSTEM_WRITE` и
`FILESYSTEM_CREATE`; политика трактует её как запись и может запросить
подтверждение. Она не принимает произвольные пути на хосте.

Начальные ограничения:

| Элемент | Ограничение |
|---|---|
| отдельный артефакт | 50 MB |
| всего артефактов на ход | 256 MB |
| артефактов на ход | 200 |
| чтение на вызов | 256 KB |
| текст сообщения | 64 KB |
| сообщений на mailbox | 100 |

Артефакты — это временные файлы вне Vault, с хешем SHA-256 и
метаданными. Mailbox содержит только текст и ссылки `artifact_id`.
В конце хода хранилище и mailbox очищаются.

## 3. Ограничения реализации

- максимум **2** активных субагента (настраивается в менеджере как
  `max_concurrent`);
- только локальные модели;
- без вложенности: реестр ребёнка исключает `agent.*`;
- абсолютный тайм-аут 5 минут, кооперативный;
- никакого бюджета токенов сверх `max_tool_calls`;
- никакого отдельного GUI;
- никакой записи в память;
- ASK ребёнка передаются пользователю с тайм-аутом 180 секунд; по
  истечении — DENY;
- артефакты и mailbox эфемерны: исчезают в конце хода;
- внутренние события ребёнка (`turn.*`, `tool.*`) имеют `agent_id` в
  аудите.

В конце хода родителя:

1. `finish_turn()` ожидает детей в течение тайм-аута;
2. отменяет тех, кто ещё активен;
3. удаляет рабочие пространства;
4. забывает задания.

## 4. Изолированные компоненты

| Компонент | Родитель | Ребёнок |
|---|---|---|
| LLM client | `harness.llm` | новый экземпляр, та же модель |
| Реестр инструментов | полный | отфильтрованный, только чтение |
| Файловая система | рабочее пространство родителя | приватное рабочее пространство только для чтения |
| Память | `MemoryStore` | `memory=None`, никаких записей |
| Артефакты/mailbox | чтение | outbox ребёнка |
| Подтверждения | пользователь | мост к пользователю, тайм-аут 180 |
| Usage | ledger родителя | отдельный ledger |
| Аудит | общий, с блокировкой | события `agent.*` |

У ребёнка нет автоматического контекста родителя: родитель должен
передать `context`.

## 5. Разрешённые инструменты

У родителя должны быть возможности `AGENT_SPAWN` и `COMPUTE`; ребёнок
не получает `AGENT_SPAWN` и поэтому не может создавать других агентов.

Реестр ребёнка включает инструменты, возможности которых являются
подмножеством:

```text
FILESYSTEM_READ
MEMORY_READ
COMPUTE
AGENT_DATA
```

Ребёнок получает `artifact.put`, `artifact.put_file` и `mailbox.send`.
Он не получает `artifact.read`, `artifact.list`, `mailbox.inbox`,
`mailbox.read` или `mailbox.ack`: они принадлежат родителю.

Явно исключены:

```text
filesystem.chdir
agent.*
```

Исключены по возможности:

- запись в файловую систему;
- создание, переименование, копирование, удаление;
- запись в память;
- сеть;
- MCP;
- shell.

## 6. Аудит

События, регистрируемые менеджером:

```text
agent.spawned
agent.policy_rejected
agent.started
agent.finished
agent.timed_out
agent.cancelled
agent.failed
confirmation.timeout
artifact.discarded
```

Основные поля:

```text
agent_id
agent
parent
task
inputs
max_tool_calls
max_seconds
status
usage
duration_ms
error
artifact
owner
kind
size
sha256
read_count
reason
```

Все события родителя и детей несут `agent_id`. События реестра и Agent
используют id агента, выполнившего действие; события менеджера добавляют
`agent_id` и `parent`. `agent.policy_rejected` выдаётся, если у spawn нет
строго более ограничительной политики.

`artifact.discarded` выдаётся в конце хода для каждого артефакта, не
сохранённого через `artifact.save_to`:

```text
reason=unread                → ни разу не читался
reason=read_but_not_saved    → прочитан, но не экспортирован
```

`confirmation.timeout` выдаётся, если ASK ребёнка остаётся без ответа
180 секунд; результат — DENY. GUI показывает запрос с
`agent_id`/`parent_id`, и родитель не может его разрешить.

Экспортированные артефакты не порождают событие: файл уже находится в
рабочем пространстве родителя. Содержимое никогда не записывается в
аудит.

`AuditLog.record` защищён блокировкой, поэтому параллельные записи не
переплетают хеш-цепочку.

## 7. Конкурентность

- отдельные потоки для детей;
- предел `max_concurrent = 2`;
- блокировка на словаре заданий;
- никаких состояний гонки на файловой системе: рабочие пространства
  разделены;
- никакого совместного использования `MemoryStore`, песочницы или клиента
  LLM;
- локальный провайдер с параллельными запросами;
- `agent.wait` блокирует только вызывающего, но не других детей.

## 8. Тесты

`tests/test_subagents.py` покрывает:

- выполнение с инструментами только для чтения;
- исключение записи и `agent.*`;
- передачу контекста;
- копирование входных данных в приватное рабочее пространство;
- отказ при превышении `max_concurrent`;
- два параллельных субагента;
- ошибку построения провайдера;
- события аудита.

Живой тест, выполненный с LM Studio и `gemma-3-27b-it`: два параллельных
субагента завершены, у каждого отдельный usage.
