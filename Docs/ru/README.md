# H.A.G.A.R.

Универсальный агентный harness для устойчивых ИИ (General Resilient Agentic Harness for AIs)

# 0. Как всё началось: безопасность

Я создал HAGAR потому, что ни один другой harness для ИИ не изолировал мои файлы по умолчанию. Будь то DeepSeek, Claude Code, AutoGen или что-то ещё, если оставить их без присмотра, все они в конечном счёте открывают вашу файловую систему для LLM. Именно ВЫ должны устанавливать ограничения, и делать это правильно, иначе последствия будут вашей проблемой. Ни один из этих инструментов не гарантирует, что ваши данные не будут прочитаны для неясных целей, по ошибке или по обеим причинам. И если это делает не сам harness, то это может сделать тот классный плагин, тот очень полезный навык или любое другое дополнение, которое вы только что установили...

**HAGAR переворачивает этот подход: именно ВЫ определяете, что LLM могут видеть, писать или искать, и где.** Ни одна LLM не может прочитать или записать что-либо за пределами каталогов, которые вы явно указали как читаемые или записываемые в файле конфигурации. Если каталога нет в разделе `[filesystem]` конфигурации, его не существует: для LLM это так, как если бы его не было.

Во время разработки HAGAR у меня возник ещё один вопрос: зачем LLM вообще нужно взаимодействовать с операционной системой? В мире искусственного интеллекта настоящим узким местом производительности являются вызовы модели, которые могут занимать секунды (иногда МНОГО секунд). Прямой доступ к операционной системе позволяет сэкономить лишь несколько миллисекунд: стоит ли ради этого рисковать? Мой ответ — нет.

По этой причине **HAGAR делает всё возможное, чтобы изолировать LLM от операционной системы.** Любое взаимодействие с файлами, памятью или самой машиной происходит через специальные инструменты (на основе протокола MCP или встроенные непосредственно в HAGAR). ИИ не знает, в какой операционной системе он работает, и не должен никогда это знать: если бы существовал способ, которым ИИ мог бы определить операционную систему, в которой работает, несмотря на изоляцию HAGAR, я считаю это уязвимостью безопасности и приму меры к её исправлению (или, по крайней мере, к документированию проблемы для информирования пользователей).

|Harness	|Видит ФС хоста	|Видит ОС		|Изоляция	  |
|-----------|---------------|---------------|-------------|
|Claude Code|Частично		|Да 	 		|Разрешения	  |
|Codex CLI	|Частично		|Да 	 		|Песочница	  |
|OpenHands	|Нет				|Да 	 		|Docker		  |
|E2B		|Нет				|Да				|VM/Container |
|`HAGAR`	|`Нет`			|`Нет`			|`Виртуальная ФС`|

**Другие harness пытаются дать LLM компьютер: HAGAR говорит LLM, что компьютера не существует.**
ИИ должны сосредоточиться на управлении знаниями, а не на технических деталях (хотя они очень хороши в обоих). Чем больше фреймворк может автоматизировать, тем меньше требуется рассуждений (и токенов). Так даже самые маленькие модели могут раскрыть свой полный потенциал.

Или, иначе говоря: для LLM HAGAR — это реальность.

# 1. Видение проекта

HAGAR — это harness для LLM, разработанный на Python и предназначенный для безопасного выполнения языковых моделей.

Цель — не просто предоставить интерфейс чата для LLM, а создать операционную среду ***безопасную и защищённую***, в которой LLM может использовать инструменты, обращаться к постоянной памяти и взаимодействовать с внешними системами — и всё это без прямого доступа к реальным ресурсам хост-машины — предотвращая или, по крайней мере, смягчая наиболее распространённые ошибки.

Поэтому я принял принципы и методологии как из области информационной безопасности (принцип наименьших привилегий, триада CIA), так и из области HMI/HCI (взаимодействие/интерфейс человек-машина, типичный для промышленного оборудования) и когнитивной эргономики, применив их к проектированию среды, в которой работает LLM: как и в случае с работой людей, дополнительная цель HAGAR — создать для LLM среду, где делать правильно легко, а ошибаться трудно.

На основании изложенного и с целью установить общее правило поведения для любого будущего развития этого программного обеспечения, я формулирую здесь **Четыре закона HAGAR**:

## 1.1 Первый закон HAGAR
**LLM по определению ненадёжна.** Это не значит, что она злонамеренна или бесполезна, но её работа имеет вероятностную природу. Следовательно, каждое её утверждение должно быть проверено, а каждое её действие должно быть ограничено.

## 1.2 Второй закон HAGAR
**Инструменты надёжнее LLM.** Если файловая система говорит, что файл существует, значит, он действительно существует. Если инструмент возвращает размер файла, этот размер реален. LLM интерпретирует, но инструменты измеряют.

## 1.3 Третий закон HAGAR
**Состояние должно существовать вне «разума» LLM.** Реализуя такие компоненты, как `ToolRegistry`, `MCP`, `FilesystemSandbox`, `Memory` и `PermissionEvaluator`, мы переносим знания и контроль за пределы самой модели. Это соответствует стандартным практикам для систем, в которых безопасность является критическим требованием.

## 1.4 Четвёртый закон HAGAR
**Каждое действие должно быть объяснимо задним числом.** По этой причине HAGAR реализует *журнал аудита*: когда что-то пойдёт не так — а рано или поздно это случится — вопрос должен быть не «Почему LLM сошла с ума?», а «Какие допущения она приняла?», «Какой инструмент она использовала?», «Какие данные были ошибочными?». Иными словами, должна быть возможность провести анализ инцидентов, точно как в авиации. HAGAR признаёт эту необходимость и всегда будет давать инструменты для этого.

## 1.5 Архитектура программного обеспечения

Со структурной точки зрения HAGAR основывается на пяти фундаментальных принципах:

- разделение между моделью и операционной системой;
- безопасность по умолчанию (*security by default*);
- плагинная архитектура;
- независимость от любого конкретного поставщика LLM;
- расширяемость через инструменты (*tools*) и MCP (Model Context Protocol).

# 2. Абсолютные запреты

Модели категорически запрещено:

- напрямую обращаться к файловой системе хоста;
- выполнять команды в настоящем shell операционной системы;
- получать привилегии выше определённых в конфигурации;
- знать реальную операционную систему.

Все операции должны происходить только через инструменты, зарегистрированные и контролируемые harness.

# 3. Разработка

## 3.0 Установка и CLI

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -e .
```

`pip install -e .` объявляет пакеты `core`, `llm`, `memory` и
`local_tools` и устанавливает команду `hagar`:

```powershell
hagar --config hagar.yaml
hagar --model qwen3:8b
hagar --no-memory
hagar --no-native-tools
hagar --version

# GUI web locale
hagar web
hagar --config hagar.yaml web --port 8765
```

Веб-GUI использует `http://127.0.0.1:8765/`, случайный токен для API,
модальные подтверждения ASK, остановку хода, загрузку изображений, вкладки для чата,
истории, вывода инструментов, аудита, размышлений и воспоминаний, а также суммарные токены
сессии в боковой панели. Подробности см. в `MANUAL.md` §3.0.

Конфигурация ищется в следующем порядке: параметр `--config`,
переменная окружения `HAGAR_CONFIG` и, наконец, файл `./hagar.yaml`.
Кроме того, можно использовать `python -m hagar`, работая напрямую с исходным кодом.

## 3.1 Структура каталогов

```
hagar.py            Скрипт запуска harness
hagar.yaml          Скрипт конфигурации по умолчанию
policy.yaml			Конфигурация разрешений для инструментов (встроенных и MCP)
core/               config, agent, журнал аудита, registry, sandbox, service и веб-сервер
llm/                бэкенды LLM (Ollama, LM Studio, DeepSeek, OpenAI, Claude, Gemini), клиент MCP
memory/             память SQLite (sqlite_store.py) и legacy markdown-бэкенд
web/                HTML, CSS и JavaScript локального GUI
tests/              набор тестов pytest
tools/              вспомогательные средства разработки (test runner, sandbox shim, бенчмарк моделей)
local_tools/        встроенные инструменты; built-in проходят через local_tools/plugins.py
core/plugins.py     контракты и обнаружение плагинов (hagar.tools, hagar.llm)
core/subagents.py   менеджер синхронного и read-only субагента MVP
llm/plugins.py      встроенные провайдеры LLM, зарегистрированные как плагины
```

## 3.2 Бэкенды LLM

`model.provider` выбирает бэкенд. Схемы инструментов (tool), преобразование сообщений и нативные или fallback-пути обрабатываются в `llm/base.py`; поэтому смена провайдера не требует изменений в инфраструктуре выполнения (harness).

Нативный вызов инструментов — настройка по умолчанию для всех бэкендов. Если модель отклоняет этот режим (возвращая ошибку HTTP 400, 404 или 422), агент переходит на текстовый JSON-протокол на всю сессию; можно принудительно использовать текстовый протокол, установив `model.native_tools: false` или передав аргумент `--no-native-tools`.

| provider   | транспорт                    | ключ API               |
|------------|------------------------------|------------------------|
| `ollama`   | нативный `/api/chat`         | нет                    |
| `lmstudio` | локальный, совместимый с OpenAI | нет (опционально)  |
| `deepseek` | REST, совместимый с OpenAI   | `DEEPSEEK_API_KEY`     |
| `openai`   | OpenAI Chat Completions      | `OPENAI_API_KEY`       |
| `claude`   | Anthropic Messages API       | `ANTHROPIC_API_KEY`    |
| `gemini`   | Generative Language API      | `GEMINI_API_KEY`       |

`chatgpt` — это алиас `openai`. Подписка ChatGPT не даёт доступа к API: нужны ключ OpenAI и кредит API. В LM Studio должен быть запущен локальный сервер и загружена модель; endpoint по умолчанию — `http://localhost:1234/v1`. Если сервер LM Studio требует ключ, можно задать `LMSTUDIO_API_KEY` или `model.api_key_env`; иначе он не нужен.

С LM Studio нативный вызов инструментов зависит от модели и её шаблона: некоторые модели принимают запрос, но отвечают текстом вместо выдачи `tool_calls`. В этом случае используйте `model.native_tools: false` (текстовый JSON-протокол) или модель с поддержкой инструментов.

Имена моделей, поддерживаемые сейчас для DeepSeek: `deepseek-flash` (по умолчанию) и `deepseek-v4-pro`; старый `deepseek-chat` больше не принимается. Live-тест использует `deepseek-flash`, если он не переопределён переменной `HAGAR_LIVE_DEEPSEEK_MODEL`. Скрипт `tools/diagnose_deepseek.py` позволяет проверить DNS, формат ключа и endpoint, не показывая сам ключ.

Ключи читаются только из переменных окружения и никогда из файла YAML. Если имя переменной по умолчанию не подходит для ваших нужд, можно указать другое с помощью `model.api_key_env`. Параметр `model.host` задаёт базовый URL провайдера (со значением по умолчанию, специфичным для каждого; например, Ollama использует `http://localhost:11434`, а LM Studio — `http://localhost:1234/v1`), `model.timeout` — это тайм-аут HTTP в секундах (по умолчанию 120), а `model.max_tokens` применяется только к Claude (со значением по умолчанию 1024).

```yaml
model:
provider: gemini
name: gemini-2.0-flash
```

Каждый бэкенд нормализует диалог согласно своему формату: Claude получает системные сообщения в специальном поле `system` и чередующиеся ходы, а Gemini получает `systemInstruction` и роль `model`. Общий протокол между агентом и клиентом использует исключительно роли `user` и `assistant`.

## 3.3 Журнал аудита

Каждая сессия добавляет записи в формате JSON Lines по пути, указанному в `audit.path` (значение по умолчанию: `logs/audit.jsonl`, разрешается относительно файла конфигурации):

```yaml
audit:
enabled: true
path: logs/audit.jsonl
max_field_chars: 2000
```

Регистрируемые события: `harness.start`, `turn.start`, `llm.tool_choice`, `llm.protocol_error`, `llm.repaired`, `llm.repair_failed`, `tool.call`, `tool.result`, `turn.answer`, `turn.error`, `turn.stop`, `mcp.loaded`, `mcp.failed`, `llm.failed`, `harness.stop`. Отсутствие события `harness.stop` в последней сессии указывает на то, что процесс был принудительно завершён или упал.

Каждая запись включает метку времени UTC, ID сессии и, где уместно, ID хода, общий для всех событий, относящихся к одному запросу. Усечение данных регулируется параметром `audit.max_field_chars`; ключи API никогда не записываются в журнал.

Журнал предназначен для обращения к нему после инцидента, а не для чтения моделью. Поскольку он может содержать содержимое файлов, прочитанных через инструменты доступа к файловой системе, с ним нужно обращаться с той же осторожностью, что и с самим рабочим пространством (workspace).

## 3.4 Разрешения и `policy.yaml`

Каждый вызов инструмента авторизуется до его выполнения. Инструмент объявляет свои
**capability** (`FILESYSTEM_READ`, `FILESYSTEM_WRITE`,
`FILESYSTEM_CREATE`, `FILESYSTEM_DELETE`, `MEMORY_READ`,
`MEMORY_WRITE`, `MCP_CALL`, ...); **субъект** (агент) определяет
правила, сопоставляющие эти функциональные возможности с `allow` (разрешить), `ask` (спросить) или `deny` (запретить),
возможно ограниченные по имени инструмента, префиксу пути или пространству имён.

```yaml
version: 1
subjects:
assistant:
default: deny
rules:
- capabilities: [FILESYSTEM_READ]
effect: allow
tools: ["filesystem.*"]
- capabilities: [FILESYSTEM_WRITE, FILESYSTEM_CREATE]
effect: ask
paths: ["note"]
```

Опция `ask` создаёт запрос в консоли вида `lo faccio? (y/N)` (со значением по умолчанию `N`); протокол `ConfirmationProvider` позволяет также реализовать модальное диалоговое окно в графическом интерфейсе (GUI).
Файл политик читается до создания LLM: если он отсутствует или
недействителен, каждая политика устанавливается в `DENY`, ошибка регистрируется в журнале аудита (`policy.failed`) и отображается в чате, при этом harness продолжает работать.

## 3.5 Память

Память — это локальная база данных SQLite, и она является источником истины:
сессии, ходы, навыки и сводки. Модель может сохранять воспоминания с помощью
`memory.create_skill`, перечислять их с помощью `memory.list_skills` и обращаться к
предыдущим ходам через `memory.get_context`.

```yaml
memory:
  enabled: true
  backend: sqlite
  context_turns: 10
  max_skill_chars: 4000
```

База данных по умолчанию — `%LOCALAPPDATA%/Hagar/memory.db` (или
`HAGAR_MEMORY_DB`). Бэкенд `markdown` остаётся только для совместимости.
Записи проходят через движок политик. Команды `/memory` в CLI
позволяют просматривать чаты, навыки и статистику.

## 3.6 Инструмент решений

`decision.choose` задаёт вопрос с фиксированным выбором и возвращает метку,
вероятности и провайдера. Поддерживает LLM-арбитра (локальный или удалённый) и
локальный линейный классификатор. Подробности в [DECISIONS.md](DECISIONS.md).

## 3.7 Паспорта и бенчмарки моделей

`/models test` измеряет задержку, структурированный JSON и вызов инструментов и сохраняет
JSON-паспорт с оборудованием и датой последней проверки. Подробности в
[MODEL_CARDS.md](MODEL_CARDS.md).
